# Contributing to vscode-mcp

Thank you for helping improve `vscode-mcp`. The project treats editor contents and local
workspace metadata as sensitive, so small changes still need explicit boundary tests.

## Before changing code

Read [AGENTS.md](./AGENTS.md), the relevant architecture decision records, the
[security model](./docs/security-model.md), and the
[1.0 tool contract](./docs/tool-contract-v1.0.md). `AGENTS.md` is normative for
contributors and coding agents.

Material changes to the transport, trust boundary, supported environments, public tool
surface, or distribution model require a proposed ADR and maintainer agreement before
implementation. Version 1.0 exposes bounded mutation plus configured task and named
run/debug controls under separate session grants. Generic shell, terminal input, Git,
arbitrary VS Code command, and arbitrary DAP access remain out of scope.

## Development setup

Use Node.js 22 and the pnpm version pinned in `package.json`. pnpm is the only supported
package manager.

```sh
corepack enable
pnpm install --frozen-lockfile
pnpm audit
pnpm check
pnpm build
pnpm test:extension
```

Run `pnpm doctor` to validate the local toolchain. `pnpm dev` starts the protocol,
extension, and server watchers after a clean initial build. Bundles rebuild
automatically; reload the Extension Development Host after extension changes and restart
the MCP client after server changes. The complete loop, local VSIX installation, and
packaged-pair test are documented in [docs/development.md](./docs/development.md).

Use `pnpm install` without `--frozen-lockfile` only when intentionally changing a
dependency. Do not add npm, Yarn, Bun, or another lockfile.

## Change guidelines

- Keep strict TypeScript and validate `unknown` at every process or provider boundary.
- Preserve package ownership: VS Code APIs in `extension`, MCP `stdio` behavior in
  `server`, and shared wire contracts in `protocol`.
- Add success, failure, cancellation, limit, and workspace-escape tests for tool work.
- Never put tokens, endpoints, source content, provider output, absolute paths, or
  environment data in logs, errors, fixtures, snapshots, issues, or pull requests.
- Do not add telemetry, network listeners, persistent content logs, or uncontracted
  mutation/execution paths.
- Keep dependencies exact, justified, audited, and represented in third-party notices.
- Update documentation and accepted contracts with the implementation they describe.

Run `pnpm check`, `pnpm build`, the extension-host tests, and relevant focused tests
before requesting review. A local release candidate can be produced only with the
repository release scripts; generated `artifacts`, `dist`, `out`, coverage, and
`.vscode-test` files are not committed.

The complete local release process is documented in
[docs/release-process.md](./docs/release-process.md). `pnpm package:release` is valid
only after every package is version `1.0.0`; it does not publish or upload anything.
`THIRD_PARTY_NOTICES.md` is generated by that process and must not be edited manually.

## Security reports

Do not file a public issue for a suspected vulnerability. Follow
[SECURITY.md](./SECURITY.md) and share the smallest redacted reproduction that proves
the boundary failure.
