# ADR 0006: Atomic v0.2 contract promotion

- Status: Superseded by ADR 0004, ADR 0007, and the accepted 1.0 full-IDE contract
- Date: 2026-07-11
- Scope: Promotion of the accepted additive read contract after the first 1.0 release

The maintainer subsequently moved agent-ready reads and the complete IDE surface into
the first 1.0 release. The active runtime now advertises exact contract `1.0.0` and all
39 MCP tools atomically. This ADR remains only as the historical promotion analysis;
none of its post-1.0 sequencing or inactive-runtime statements are current.

## Context

ADR 0005 accepts three additive read tools under exact tool contract `0.2.0`. Their
schemas, extension services, stable VS Code adapters, bounded scanner, internal result
envelopes, additive router, and listener-generation runtime now exist behind explicit
v0.2-only modules. The published/runtime contract remains `0.1.0` with eleven MCP tools.

The current registry advertises one exact tool-contract version per VS Code window. The
authenticated hello requires the bridge and extension to present that same version.
Serving 0.1 and 0.2 behavior from one advertised listener would weaken exact-pair
validation, make capabilities connection-dependent, and complicate registry selection.

The repository also requires its first public state and first GitHub Release to be
version `1.0.0`, while ADR 0005 deliberately defines v0.2 as post-1.0 behavior.
Activating v0.2 before that release would contradict the accepted publication sequence
unless the maintainer explicitly revises it.

## Proposed decision

Promote v0.2 as one atomic bridge/extension release after the first 1.0 publication. Do
not add a runtime compatibility flag or dual-contract listener.

1. The extension listener advertises exact contract `0.2.0` in its registry record,
   instance descriptor, authenticated hello result, and capabilities.
2. The matching bridge requests exact contract `0.2.0`, accepts only a matching hello,
   and registers fourteen MCP tools: the eleven unchanged v0.1 tools plus the three
   additive read tools.
3. A listener generation creates one cryptographic cursor key only after its instance ID
   exists. File discovery and text search share that codec. Stop, trust loss,
   disablement, workspace identity change, or extension shutdown destroys the runtime
   and key.
4. The ten legacy extension tools continue through the existing hardened router. The
   three new tools use the isolated v0.2 read router. The additive composition validates
   every invocation and result against the v0.2 IPC schemas before transport.
5. Registry discovery remains exact. A 0.1 bridge does not select a 0.2 instance, and a
   0.2 bridge does not select a 0.1 instance. Mixed packaged pairs fail closed with the
   existing safe version-mismatch behavior.
6. Promotion changes the package/release version in the same reviewed snapshot. The
   recommended first v0.2 product release is semver `1.1.0`; this remains unapproved
   until the first `1.0.0` publication is complete.
7. Downgrade means reinstalling the complete version-matched 1.0 bridge/VSIX pair. No
   persisted index, cursor, migration state, or compatibility shim is required.

## Promotion gates

Before changing the active constants or registration:

- complete v0.2 hello, registry filtering, IPC dispatch, bridge gateway, MCP SDK
  registration, byte-bound, cancellation, and exact mixed-pair tests;
- map every applicable v0.2 security criterion to repeatable evidence;
- run the implemented agent traces against a packaged matching pair;
- complete a post-implementation security review with no unresolved high-severity
  finding;
- publish and verify the accepted first `1.0.0` release, or explicitly revise the
  publication policy; and
- approve the product/package version for the additive release.

## Historical implementation boundary at the time of this ADR

The repository contains an explicit `ipc-schemas-v0.2` protocol subpath, a thirteen-tool
extension capability schema, strict new-tool IPC results, an additive extension router,
and an unregistered listener-generation runtime bundle. None is imported by the active
extension controller, IPC listener, registry publisher, bridge gateway, or MCP SDK
registration. `TOOL_CONTRACT_VERSION` remains `0.1.0`.

## Consequences

- Exact-pair security stays simple and observable.
- Existing 1.0 artifacts and clients never discover tools they cannot call.
- Cursor lifetime aligns with the authority-bearing listener rather than short-lived IPC
  connections.
- The inactive implementation can be tested thoroughly before a one-snapshot promotion.
- Users cannot opt into v0.2 early through hidden settings or mismatched local files.
